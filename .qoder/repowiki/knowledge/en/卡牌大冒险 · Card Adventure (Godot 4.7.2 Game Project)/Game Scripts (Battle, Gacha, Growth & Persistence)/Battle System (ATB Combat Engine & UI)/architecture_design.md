Three-file split with strict separation of concerns:
- `battle_ctx.gd` is an autoload `Node` holding per-battle transient state (`stage_id`, `atk_bonus`, `seed_override`, buff metadata) so the stage-select screen and the battle scene can exchange data without persisting it to SaveDB.
- `battle_core.gd` (`class_name BattleCore`, extends `RefCounted`) is the deterministic simulation engine. It owns the unit array, an ATB clock (`_clock`), RNG seeded from `BattleCtx.seed_override`, and exposes `setup()` / `step()` / `run_all()`. All combat rules (role defaults via `_role_action`, target resolution via `resolve_targets`, damage formula in `compute_damage`, shield/buff/heal/ult dispatch in `_execute`) are driven by config dictionaries from `GameDB`; new monsters require no code changes. The public contract with the UI is a list of event dictionaries (`t: action|damage|heal|shield|buff|stun_apply|death|end`).
- `battle.gd` extends `Control` and is the Godot scene controller. It builds the procedural background, 3×3 grid, unit tokens, team cards, log panel, and result overlay using `tools/ui_kit.gd`. Its `_process` loop calls `core.step()` every `ACTION_SECONDS / SPEEDS[_speed_index]` seconds and feeds the returned events into `_play`, which only animates — no numeric decisions. A comment enforces the invariant: "任何数值判断都不在这里做".

Dependency direction: `battle.gd` → `BattleCore` + `BattleCtx` + `GameDB` + `UI`; `BattleCore` → `GameDB` + `growth_core.gd` + `RealmDB`; `BattleCtx` has no game-code dependencies. This keeps headless smoke tests runnable against `BattleCore` alone while the same seed produces identical logs and results as the on-screen run.
